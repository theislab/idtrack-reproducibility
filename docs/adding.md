# Adding a family or a benchmark

Every benchmark of this repository has the same parts in the same places, and `idtrack-repro check` fails until a new one has them all. This page is the checklist.

## Layout

| part | where | what |
| --- | --- | --- |
| code | `src/idtrack_reproducibility/families/<family>/` | a package: the generator of the query sets, the family's truth reader, its own rules and causes, its limitations map; modules run as `python -m idtrack_reproducibility.families.<family>.<module>` |
| common machinery | `src/idtrack_reproducibility/families/*.py` | the query line, the adapter, the runner, the scorer, the reports, the comparison, the causes and the limitations builder ([the common machinery](families/f0.md)); a family uses them and never copies them |
| methods | `docs/families/<family>.md` | what is asked, the truth, the strata and their sizes, the rules, how to reproduce it from scratch, what it cannot judge |
| tests | `tests/test_family_<family>.py` | unit tests of the family's own logic on small invented cases where a plausible wrong version fails; no data root needed |
| data | `<families>/<family>/` of the data root | `queries/<organism>/<set>.{parquet,jsonl.gz}` with `<set>.manifest.json`, `runs/<tree>/<organism>/` (answers, outcomes, tables), other inputs the family computes (a selection, patterns) |
| manifests | `manifests/families/<family>.tsv` | every data file of the family that a result rests on: path in the data root, size, sha256, source, time ([data](data.md#manifests)) |
| results | `results/<family>/<tree>/<organism>/` | the small tables a manuscript cites, generated by `idtrack-repro results`, each listed in `results/index.tsv` and `results/provenance.tsv` |
| limitations | `results/limitations/limitations.tsv` | the family's rows of the known-limitations table, generated from its causes |
| registry | `results.toml` | the family's current scored runs (one per tree and organism), which `idtrack-repro results` reads |

Other benchmarks follow the same pattern: the accuracy harness (`harness`), the regression corpus (`corpus`), the weakness hunts (`hunts`) and the performance measurements (family `h`) each have their code package, their methods document in `docs/`, their tests and their results under `results/<name>/`.

## Names

- **Families**: one lower-case word of letters and digits (`f0`, `astar`, `a`, `e`); the hardest lineages are `astar` (A* in prose).
- **Strata**: lower case with underscores, prefixed by the family's stratum code where the family has one (`a1_versioned`, `e2_zerowidth`); the harness's strata are its kinds (`retired_split`).
- **Sets**: `<stratum or group>_v<n>` for a published set, `<set>_r<n>` for a revision set of it (a family's own scheme is kept once published: published names never change); the harness's sets are `v<n>` in publication order.
- **Trees**: the short commit of idtrack (`d4c2dda`, `71690ab`), with a suffix for a variant run of the same tree (`d4c2dda_s110`: a graph of snapshot 110).
- **Runs**: `runs/<tree>/<organism>/`.
- **Result files**: lower case, `[a-z0-9_.-]`, the table's kind first (`report.tsv`, `scores.tsv`, `travel_report.tsv`, `moved_d4c2dda_to_71690ab.tsv`).

## The query line and the report

A family's query line is the common line ([the common machinery](families/f0.md#the-query-line)): the harness's fields plus `family`, `stratum`, `unit` (the cluster of the bootstrap) and the family's own fields. Its report is the common `report.tsv` (per stratum and view: counts, rate, Wilson and cluster-bootstrap intervals, units, latency). A family that needs another table adds it beside these, never instead of them.

## Rules of writing

- Truth never comes from idtrack: every expectation is read from Ensembl's or an authority's files, recorded in the truth store with its URL, size, checksum and time.
- A published set is never rewritten; a change of truth is a revision set.
- No machine path: every location comes from the configuration (`idtrack_reproducibility.config`); jobs go through `idtrack_reproducibility.jobs.submit`.
- Cite idtrack's behaviour by its rule's name ([rules](rules.md)); add a rule there when a family needs one.
- Every number in a document is copied from a generated result, and the document names the result file.

## Steps

1. Write the generator and publish the sets on the data root (`lines.publish`); write the methods document while the sets are drawn.
2. Run the family exhaustively on the reference tree's graphs (`idtrack-repro run`), score it (`idtrack-repro score`), classify the wrong answers (`idtrack-repro causes`). Development stages are measured by the family's panel, the final tree exhaustively again ([Measurement design](methods.md#measurement-design)); a panel run's registry entry says `scope = "panel"`.
3. Add the family's limitations map (and, if its rows need more than its causes, its own builder), add the family to `known_limitations.BUILDERS`, and generate the table (`idtrack-repro known-limitations`).
4. Add its runs to `results.toml`; `idtrack-repro results` writes its results, the index and the provenance.
5. `idtrack-repro manifest families/<family>` writes its data manifest.
6. Tests in `tests/test_family_<family>.py`.
7. `idtrack-repro check` passes (with the data root present, also its data checks).
